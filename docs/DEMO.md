# Demo Walkthrough

A ~5-minute live demonstration of the UEBA Insider Threat Detection system on
synthetic data. No raw dataset is required. Everything below runs offline.

## Before the demo: prepare the data (~1 minute)

Run these from the repository root with the virtual environment active (see the
[README](../README.md) for setup). They generate synthetic logs with a planted
insider, build the risk scores and report, and start the dashboard.

```bash
# 1. Generate CERT-4.2-shaped synthetic logs and plant a known insider.
python scripts/generate_synthetic.py \
    --out-dir data/raw --n-users 300 --n-days 120 --seed 42 \
    --plant USER0005:100:usb_burst

# 2. Build risk.parquet and write reports/eval_report.md + plots (one command).
python scripts/run_eval.py

# 3. Launch the dashboard.
streamlit run app.py
```

Streamlit opens http://localhost:8501 in your browser. Keep a terminal handy to
show `reports/eval_report.md` at the end.

Tip: `USER0005` on day `100` is the planted insider (a USB-burst anomaly), so
you know exactly who the system should surface. You can plant others — e.g.
`--plant USER0012:95:after_hours_logons` — to show different anomaly types.

## The script

### 1. The pipeline in one breath (~45 seconds)

Give one sentence per layer so the audience sees the shape of the system before
the screen:

- **Profiling** — look at the raw CSVs first so parsers match the real data.
- **Ingestion** — read the event logs in chunks, aggregate to one row per user
  per day.
- **Features** — turn each user-day into 15 behavioral numbers (logon, USB,
  web, email).
- **Baselines** — learn each user's normal from their first 60–90 days, plus a
  peer baseline per role.
- **Scoring** — compare each later day to those baselines (self and peer
  z-scores) and to an IsolationForest, then fuse them into a 0–100 daily risk
  and a trailing-7-day weekly risk.
- **Evaluation** — grade the ranking against ground-truth labels (labels are
  used here only, never in training).
- **Dashboard** — the analyst's screen you are about to see.

### 2. Ranked users (~45 seconds)

Point at the main table: **users ranked by weekly risk**, highest first. This is
the triage queue — an analyst starts at the top. Note that the planted insider
`USER0005` rises toward the top because the USB burst pushed its risk up.

Point out the two controls:
- the **date control**, which sets the day in view, and
- the **risk-threshold slider**, which decides what counts as an alert.

### 3. Drill into a known insider (~90 seconds)

Select **`USER0005`**. Walk through two panels:

- **Daily-risk timeline** — the user's risk per day. Point at the spike around
  day 100 where the planted USB burst lands; the baseline period before it is
  calm.
- **Why-flagged panel** — the top contributing features for that day, each with
  its value, the user's baseline mean, and the z-score. For `USER0005` the USB /
  removable-media features dominate, which is exactly the planted behavior. This
  is the "explainability" story: the system does not just say *risky*, it says
  *why*.

### 4. Move the threshold slider (~45 seconds)

Drag the **risk-threshold slider** up and down and watch the **alerts-per-day**
view change. Higher threshold → fewer, higher-confidence alerts; lower threshold
→ more alerts and more noise. This frames the precision/recall trade-off an
analyst actually tunes in practice.

### 5. Evaluation table and limitations (~60 seconds)

Switch to `reports/eval_report.md` (generated by `python scripts/run_eval.py`).
Show the side-by-side comparison of the three variants — **z-score only**,
**IsolationForest only**, and **fused** — on recall@20, recall@50,
precision@20, and user-day PR-AUC. The point: fusion combines statistical
deviation with machine-learned anomaly structure, and the table lets you compare
them honestly. Note there is deliberately **no plain accuracy**: with insiders a
tiny minority, accuracy would be misleadingly high.

Close with the limitations (the same ones documented in
[`ARCHITECTURE.md`](ARCHITECTURE.md)):

- Detection is **unsupervised** and **ranking-based** — it surfaces anomalies
  for an analyst to review, not automated verdicts.
- It depends on a stable baseline period; users with too little history are
  flagged as having an insufficient baseline and excluded from scoring.
- Synthetic data makes the demo reproducible but is simpler than the real CERT
  r4.2 behavior; numbers on the real dataset will differ.
- Labels are for evaluation only; the detector never trains on them.

## Reset between runs

To start clean, delete the generated artifacts and regenerate:

```bash
# remove generated data + reports, then re-run the prep commands above
rm -rf data/raw/* data/processed/* reports/eval_report.md reports/*.png
```

On Windows PowerShell:

```powershell
Remove-Item data\raw\*, data\processed\*, reports\eval_report.md, reports\*.png -Force -ErrorAction SilentlyContinue
```
